# 守护单实例缺陷修复记录（2026-10-25）

> 影响面：wu2198 补抓任务的**守护/自愈链路**，不涉及抓取脚本本身、不涉及已落盘数据。
> 抓取节奏全程未受影响：修复期间进度持续增长（13:53 的 3151 篇 → 14:04 的 3161 篇），
> 严格串行、约 2.1–2.2 篇/分钟（低于 15 秒/篇 的合规上限）。

## 一、发现经过

排查"守护是否有重复实例"时，用**包含 `pythonw.exe`** 的进程枚举看到 5 个守护进程：

| PID | 解释器 | 状态 |
| --- | --- | --- |
| 11036 | `python.exe` | 有效（`watchdog.pid` 指向它，能正常拉起/续跑抓取） |
| 22852 / 16144 / 23460 / 23064 | `pythonw.exe` | **惰性重复**：能启动、但永远无法拉起抓取进程 |

其中 PID 23460 的启动时间（13:23:04）与 `heal.log` 中"检测到停滞，拉起守护"完全对应。

## 二、两个根因（互相放大）

### 根因 1：进程枚举只认 `python.exe`，`pythonw.exe` 不可见

三处枚举都写了 `-Filter "name='python.exe'"`：
`tools/watchdog_run.py::_ps_python_cmds`、`tools/self_heal.py::ps_lines`、`temp/switch_gap.py`。

而计划任务 `\FxzBlogCrawler-SelfHeal` 的动作是：

```
"C:\Program Files\fxz-desktop\resources\runtimes\python\pythonw.exe" ...\tools\self_heal.py
```

`self_heal.py` 用 `sys.executable` 拉起守护 → **生产环境的守护是 `pythonw.exe`**。
后果有二：

1. **自愈链实际是断的**。`watchdog_run.probe()` 有一道正确的自检——"枚举里必须能看到自身 PID，
   否则结论记为 `unknown` 并按『有抓取进程』处理（fail-closed）"。`pythonw` 守护看不到自己
   → 永久 `unknown` → **永远不敢拉起抓取进程**。证据是守护日志：

   ```
   [13:52:49] 【拒绝启动】无法确认是否已有抓取进程（枚举自检失败：未查到自身 PID 16144，结果不可信）→ 按“有”处理，30 秒后重试。
   [13:52:52] 【拒绝启动】... 未查到自身 PID 23064 ...
   [13:53:02] 【拒绝启动】... 未查到自身 PID 22852 ...
   ```

   也就是说：此前若手工那个 `python.exe` 守护（11036）退出，系统会**永久停摆**，
   计划任务每 10 分钟拉起的新守护仍然是不可见的 `pythonw`，照样不干活。

2. **PID 文件被反复误判为"过期"**。`_pid_is_our_watchdog(pid)` 拿 PID 去 `python.exe` 列表里核对，
   核对 `pythonw` 守护必然返回 False → 判定"PID 文件过期"→ 删除 → 再拉起一个
   → 重复守护不断累积（本次累积 4 个）。

### 根因 2：单实例只靠 `watchdog.pid` 一个文件，且自愈不看"守护是否在场"

- `watchdog_run.py` 的启动互斥完全依赖 `PID_FILE` 的内容，一旦该文件被误删/误判（根因 1 就会导致），
  互斥即失效。
- `self_heal.py` 在"无抓取进程"分支**完全不检查 `guards`**，于是每 10 分钟就补一个守护。
  两缺陷叠加 → 每 10 分钟稳定制造一个重复守护。

## 三、修复内容

| # | 文件 | 改动 |
| --- | --- | --- |
| 1 | `tools/watchdog_run.py` | 枚举过滤条件改为 `name='python.exe' or name='pythonw.exe'`；补写事故注释 |
| 2 | `tools/self_heal.py` | 同上；新增分支"无抓取进程但已有 N 个守护在场 → 交给守护自行恢复，不重复拉起"，并写 `ALERT.md` |
| 3 | `tools/watchdog_run.py` | **新增身份互斥闸** `_other_watchdogs()`：枚举"还有谁在跑 `watchdog_run.py`"（不依赖任何文件状态）。`--detach` 前拒绝重复启动；前台开工前拒绝；写入 PID 文件后**再复查一次**以覆盖启动竞态，且只在 PID 文件确实是自己写的时才清理它（避免删掉对方的 PID 文件再次引发根因 1 的连锁） |
| 4 | `temp/switch_gap.py` | 同一枚举盲点修正（换节点脚本，保证换节点时看到的进程数是真的） |
| 5 | `tools/self_heal.py` | `save_status()` 增加 `DRY` 闸门：`--dry-run` 一律不写状态文件。**这是本次验证过程中自查出来的自身缺陷**——离线分支测试的假状态（抓取 0/守护 0）曾被写进生产 `heal_status.json`，会误导查看者与报表 |

互斥闸采用 **fail-closed**：枚举不可信时一律拒绝启动（宁可漏动、不可双开）。

## 四、验证

1. **清理**：终止 4 个惰性重复守护（22852/16144/23460/23064，`taskkill` 全部成功），
   复查进程列表 → 恰好 **1 守护（11036）+ 1 抓取（24504）**。
2. **单实例闸实测**：在守护运行中执行
   `python tools/watchdog_run.py --detach ...` → 输出
   `已有守护在运行（PID 11036），拒绝重复启动。` ✓
3. **枚举真实性实测**：`self_heal.py` 巡检输出由原来的 `守护 0 个` 变为 `抓取进程 1 个 | 守护 1 个` ✓
   （此前恒为 0，正是盲点的直接体现）。
4. **判定分支离线验证**（`temp/test_heal_branch.py`，monkeypatch 造假状态 + `--dry-run`）：

   | 场景 | 期望 | 实测 |
   | --- | --- | --- |
   | 无抓取进程 + 日志超时 + 有守护 | 不重复拉起 | ✓ "交给守护自行恢复，不重复拉起" |
   | 无抓取进程 + 日志超时 + 无守护 | 判定停滞、本应拉起 | ✓ 未误伤恢复路径 |
   | 无抓取进程 + 日志刚写过 | 疑似换轮，下次再判 | ✓ 宽限逻辑未变 |

   注：首次执行时该测试**并非零副作用**——假状态被写进了生产 `heal_status.json`（已按上表第 5 条修复
   `save_status` 的 `DRY` 闸门，复跑确认不再写入）。该文件会在下一次真实巡检时被覆盖为真实状态，
   不影响抓取与判定。

5. **语法检查**：三文件 `py_compile` 通过。

## 五、残留风险（已知、未消除）

1. **守护"僵而不死"时无自动兜底**：若守护进程活着但失能（如卡在枚举失败），
   `self_heal` 现在只写 `ALERT.md` 并停手，不会强杀重启。这是按"宁可漏动、不可双开"
   刻意选择的保守策略；代价是需人工看告警。本次修复后 `pythonw` 守护已具备拉起能力，
   该场景出现概率大幅下降。
2. **启动竞态的极窄窗口**：两个守护同时通过互斥闸（毫秒级）仍可能双活，靠"写 PID 后复查"
   缓解，未做操作系统级互斥（命名互斥体）。
3. **`python.exe` 与 `pythonw.exe` 混用**：整条链路仍混用两种解释器。建议后续统一为
   `python.exe`（可见性最好），本次未改动，以免在任务运行中变更启动方式。
4. **本次改动的影响面**：`watchdog_run.py` 是当前守护（PID 11036）**正在运行**的代码，
   改动只对**下次启动**的守护生效；当前守护行为不变（其自检本来就能通过）。
