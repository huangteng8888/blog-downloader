纠正一个直觉误区：**「盘中即时直播」不是早上开贴**。它由前一交易日 15:00–17:00 建帖（标题写次日），

- 早上抓只能拿到开篇声明（约 270 字），是半成品；

## 三、本次发现的问题：本地断更 139 天

**现象**：源站已更新到 2026-10-26，本地却停在 2026-06-10，缺口 **139 天 / 273 篇**，且期间无任何告警。

**根因**（实测确认，非推测）：

1. 本项目原有的 2 个计划任务**只做监控与报表，不做抓取**：
   - `FxzBlogCrawler-SelfHeal`（每 10 分钟）→ 只守护 wu2198 的 Wayback 补抓线
   - `FxzBlogCrawler-HourlyReport`（每小时）→ 只统计 Wayback 补抓进度
2. `config/bloggers.yaml` 中 4 位博主的 `schedule.enabled` **全部为 `false`**，且无代码读取该字段。
3. 结论：**项目历史上没有建立过任何"定期抓新文章"的任务**。Wayback 线之所以有自治能力，是因为它是被守护的；而新浪线的增量同步完全依赖人工触发，一旦人停手就静默停摆。

**方法论教训**：自愈体系只能发现"已知进程异常停止"，发现不了"这条链路根本没被调度"。监控覆盖率必须以**数据新鲜度**（本地最新日期 vs 源站最新日期）为指标，而不是以"进程是否在跑"为指标。

## 四、已做处置

### 1. 新增增量同步工具 `tools/sync_latest.py`

与旧的 `src/runner.py` 相比的四处关键改动：

| 维度 | runner.py | sync_latest.py |
|---|---|---|
| 列表页 | 依赖 node + `spider.js`，固定抓主页 `/u/{uid}` | 纯 curl 抓 `/s/articlelist_{uid}_0_{page}.html`，每页 50 条 |
| 停止条件 | 连续 3 页无新增 | 连续 2 页**全部早于基线日期**，可跨越断更期 |
| 正文完整性 | 无刷新机制 | `--refresh-days N` 重抓近期文章，补全直播贴 |
| 防误伤 | 无 | 新解析为空而旧文件非空时**保留旧文**，只记警告 |

其他设计要点：
- **单实例锁** `output/{uid}/.sync.lock`，锁内记录 PID，用 `tasklist` 探活（**不能用 `os.kill(pid,0)`**——Windows 下它会走 `TerminateProcess` 而真的杀进程）。
- 首次写入前备份索引为 `posts/index.json.syncbak`（已存在则不覆盖）。
- 列表页重试 3 次 + `_v=` 防缓存参数，并做**重复页检测**（实测该入口会偶发返回上一页内容、或 curl 30s 超时）。
- 正文抓取重试 2 次，单篇失败不中断整轮，失败项不写入索引，下一轮自动补抓。
- 全部动作写 `output/{uid}/sync.log`。

用法：

```powershell
# 日常增量（默认基线=本地最新日期）
python tools\sync_latest.py --uid 1300871220

# 补偿历史空档：必须显式给 --since，否则基线已推进到最新，缺口不会被发现
python tools\sync_latest.py --uid 1300871220 --since 2026-06-10 --gap 1.0

# 只统计不落盘
python tools\sync_latest.py --uid 1300871220 --dry-run
```

### 2. 修复 `src/metadata.py` 的编码缺陷（潜在损坏源）

`metadata.py` 有 4 处 `read_text()/write_text()` 未指定 `encoding`，在 Windows 下会按 GBK 处理：

- 读 `output/1300871220/posts/index.json`（31.4 MB，UTF-8）时直接 `UnicodeDecodeError` → 同步流程无法启动；
- 更危险的是**写**：一旦绕过读的问题，`write_text` 会把整份索引转成 GBK，导致其他工具（含 Wayback 链路）全部读不出来。

已固定为 `encoding='utf-8'`。实测确认该索引文件为无 BOM 的 UTF-8。

### 3. 注册定时同步任务 `FxzBlogCrawler-DailySync`

```
执行：C:\Program Files\fxz-desktop\resources\runtimes\python\pythonw.exe
参数：tools\sync_latest.py --uid 1300871220 --max-pages 3 --gap 3 --seconds 900
周期：每日 4 轮 — 10:40 / 14:10 / 17:50 / 23:10
设置：StartWhenAvailable、IgnoreNew（不叠加实例）、单次上限 1 小时
      允许电池供电启动（AllowStartIfOnBatteries）、电池中断不停止
```

**为什么是这四个时点**（依据 §2.2 的时段分布，而非拍脑袋均分）：

| 时点 | 卡住的窗口 | 覆盖篇数占比 | 该轮最坏滞后 |
|---|---|---:|---|
| 10:40 | 08–10 时（早间/周末提前建帖） | 2.8% | 2.6 小时 |
| 14:10 | 11:31–13:15 午间短评（最晚 13:15） | 35.0% | 2.6 小时 |
| 17:50 | 14–17 时午后主峰（直播 p95 17:05、策略中位 16:24） | 60.8% | 3.8 小时 |
| 23:10 | 18–23 时零散（1.4%）+ 当日兜底与终稿 | 1.4% | 5.3 小时 |

设计取舍：
- **不按整点等间隔跑**。等间隔（如每 4 小时）会在 01:30、05:30 这类**零发文时段空跑**，
  却在 12–13 时、15–16 时两个峰之间堆积近 4 小时延迟。
- **14:10 而非 13:30**：午间短评最晚 13:15 才发，13:30 会漏掉尾部落到下一轮。
- **17:50 而非 16:30**：策略贴 p95 已到 18:40，16:30 只能拿到约一半；17:50 可覆盖 94% 的策略贴与全部直播终稿。
- **23:10 是兜底轮**：18–23 时全年仅 11 篇，这一轮的真实价值是——若白天任一轮因网络失败，当晚必定重试补齐；
  同时确保直播贴以收盘后的终稿落盘。
- **不设周六跳过**：周六实测 0 篇，跳过可省 4 轮，但收益（约 1 分钟 HTTP）远小于多一套触发器带来的维护复杂度。

单轮成本实测：2–3 次列表请求 + 2 篇刷新，耗时 **17–60 秒**，日均约 2 分钟请求量，对源站可忽略。

已验证：`LastTaskResult = 0`，日志正常写入，运行中锁存在、结束后锁释放。

> 电池参数特意改为允许：Windows 计划任务默认 `DisallowStartIfOnBatteries=true`，
> 在笔记本使用电池时会**直接跳过且不告警**——这正是本次要消灭的"静默漏跑"。
> 项目原有的 `SelfHeal` 与 `HourlyReport` 仍是默认值，本次未改动；若该机器确为桌面机则可忽略此差异。

> 注：`pythonw.exe` 下 `sys.stdout` 为 `None`，`print()` 会抛 `AttributeError`。首次注册时即因此返回 1，已在 `log()` 中加 `sys.stdout is not None` 保护。

移除方式：`Unregister-ScheduledTask -TaskName "FxzBlogCrawler-DailySync"`
