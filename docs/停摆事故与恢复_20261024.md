## 二、根因：三个独立问题叠加

### 根因 1（主因）：进程被作业对象连带强杀，且**不留下任何痕迹**
- 守护与子进程**同时消失**，守护日志没有"第 N 轮结束"，子进程 stderr 为空。
- 这是典型的"进程树被外部整体终止"特征，而非崩溃或代码异常。
- 原 `--detach` 只用了 `DETACHED_PROCESS | CREATE_NEW_PROCESS_GROUP`，
  **缺少 `CREATE_BREAKAWAY_FROM_JOB`**，因此守护仍留在宿主进程的作业对象内；
  作业对象关闭时（会话轮次结束/清理）整个进程树被一起回收。
- 这也解释了为什么它能在 16:26 启动、却在 16:29 前后（恰逢上一轮对话结束）消失。

### 根因 2：过期 PID 文件造成"守护仍在运行"的假阳性，**阻止了自动重启**
- 故障后 `watchdog.pid` 残留 `19168`。
- 原判断 `proc_alive(pid)` 只问"这个 PID 号是否存在"，**不做身份核对**；
  守护被强杀后该判断仍返回"存活"，于是新守护报
  "已有守护在运行（PID 19168），拒绝重复启动"，无法恢复。
- 18:05 的权威核查已证实：`tasklist /FI "PID eq 19168"` = 无此任务，且全部
  python 进程清单中不存在该守护 —— **旧判断确实错了**。

### 根因 3：补丁器长期"等待空闲窗口"，逐篇落盘始终未生效
- 补丁器自 15:50 起一直处于"等待空闲窗口（无 wayback_resume 进程在跑）"，
  期间抓取进程连续运行，从未出现空闲窗口；**它后来也被同一次强杀清理掉**。
- 后果：你要求的"轮中被中断也不丢记录"一直**没有真正生效**，
  skip/transient 仍只在**轮末**写入 —— 这也正是"重复抓取篇数"的根源。

### 8.3 判定：外部整体终止进程（无痕）

F4+F5+F6 组合只能由一种机制造成：**进程在运行中被外部强制终止**
（`TerminateProcess` 类），因此来不及写任何收尾日志、也不产生异常栈。
且守护与子进程**同时**消失 —— 是**整棵进程树被一起终止**，而非单进程问题。

**为何指向"宿主进程回收"**（推断，中等置信度）：
- 新证据：补丁器 `temp/_patch_console.log` 结尾是 **`^C`**（16:16:12），
  说明宿主**确实会主动对其启动的后台进程投递控制事件**，并非放任不管。
- 对照实验：18:23 用同样方式重启，唯一差别是加了 `CREATE_BREAKAWAY_FROM_JOB`，

  符合"宿主作业对象(job)关闭时连带清理"的特征。
- **仍不能完全排除**宿主的其他清理实现（按命令行匹配清理、会话级清理）。

### 8.5 为什么一个小小的网络抖动会变成 95 分钟停摆

三环叠加，缺一不可：

| 环节 | 单独看是否严重 | 实际后果 |
| --- | --- | --- |
| ① DNS 瞬时不可用 → `--max-fail 8` 提前停轮 | 不严重：设计内的保护行为，60 秒后守护会续跑 | 若无 ②③，损失可忽略 |
| ② 守护与子进程被外部整体终止 | 严重：自动续跑能力同时消失 | 抓取停止且**无任何自动恢复** |
| ③ 过期 PID 文件 + 旧判断只看"PID 号是否存在"→ 假阳性 | 严重：**人工重启也被拒绝** | 18:11 修复后仍无法启动，直到修正判断 |

**结论**：停摆的直接原因是 ②（外部杀进程），而**停摆长达 95 分钟**的原因
是 ③（自愈与人工重启双双失效）。①只是暴露 ② 的触发条件，本身不是根因。
